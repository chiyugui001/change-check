# 图表规范

> 团队知识库图表唯一标准。
> 关联：[[团队知识库方案设计]] §7

---

## 1. 优先 Mermaid

所有图表优先使用 Mermaid 语法。

理由：
- 可渲染（Obsidian、GitLab 均支持）
- 纯文本，git diff 可追踪，AI 可读写
- 改一条边/节点就是改一行文本，可维护

---

## 2. Mermaid 无法表达时可用 ASCII

- Mermaid 优先，当 Mermaid 无法很好地表达意图时，可以使用 ASCII 字符画
- 不强制禁止 ASCII，按情况而定
- 目录树可保留 ASCII

---

## 3. 类型选择参考

Mermaid 所有类型都可以使用，以下只是初步判断哪种更合适的参考：

- **状态流转** → `stateDiagram-v2`
- **顺序/分支/单向数据流** → `flowchart`
- **多角色按时间往来消息** → `sequenceDiagram`
- **Git 分支图** → `gitGraph`
- **甘特/计划** → `gantt`
- **类/结构关系** → `classDiagram`

不限于以上几种，Mermaid 支持的类型都可以用。

---

## 4. 标签与节点规则

- 所有图先表达意图：涉及函数、模块、状态等代码标识的标签，第一行写具体动作、职责或状态含义，换行后写对应代码名称，不得只显示代码名称。适用于流程节点、时序图参与者与调用消息、状态节点和带代码标识的连线标签。
- Mermaid 使用 `<br/>` 换行，例如 `判断是否允许休眠<br/>unxx_lpm_allowed()`。代码名称保持源码拼写；纯业务概念不强行补函数名。
- 中文说明必须符合实际行为和调用顺序，让不熟悉架构的读者也能看懂对象、动作与结果。
- 节点标签简短，单图控制在 5-9 个主节点；复杂逻辑拆多张图，不要挤在一张里。
- 架构与调用图须按实际需要区分运行镜像、架构层和所属文件/模块；App/Boot 分区不能代替任务、板级、公共模块、协议、公共接口、平台驱动等源码归属。概览图用目录层级，调用细节图给出文件与符号，避免混用粒度。
- 流程图用分区框、时序图用参与者分组或文件标签、状态图用归属注释表达边界。跨层箭头区分调用、数据交付、回调绑定或链接替换；不为表现源码层级而添加虚假的设备状态。

---

## 5. 校验规则

新建或修改文档后，必须逐图检查第 4 节的标签规则，覆盖所有可见节点、参与者、调用消息和连线标签；不把仅供连线使用的内部节点 ID 当作可见标签。

| 检查项 | 不通过条件 |
|---|---|
| 意图说明 | 标签只显示函数、模块或状态等代码名称，缺少具体的中文动作、职责或状态含义 |
| 顺序与换行 | 意图和代码名称未分行，或代码名称出现在意图说明之前 |
| 源码对应 | 代码名称与源码不符，或中文意图与实际行为、调用顺序不符 |
| 层级与文件归属 | 所属镜像、架构层或文件/模块无法辨认，分区与源码不符，或把回调/链接关系画成直接调用 |

格式可机械检查；意图是否具体、是否符合源码须逐项复核，不能仅凭标签中含有中文判为通过。纯业务概念按第 4 节处理。
层级与归属须对照源码路径、定义位置、调用和回调注册复核；标签格式校验通过或已有分区框，均不代表架构语义通过。

校验结果按“文档路径 + 图序号”分别记录标签格式、语义复核和实际渲染的结果。任一项不通过须修正后重新校验；未检查项不得记为通过，渲染成功不能替代标签校验。
