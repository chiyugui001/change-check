# 编译流水线

只在实际编译、增量编译或设计编译方案时读取本文件。

## 0. 发现知识库契约

1. 定位根目录，确认存在根索引、规范目录或明确的知识库标识。
2. 读取 `AGENTS.md`、`_INDEX.md`、`README.md`。
3. 读取本次涉及的规范和模板；不要依赖上次会话记忆。
4. 检查工作树、当前分支和本次允许的写入范围。
5. 记录实际知识目录、待审核入口、索引位置和提交规则。

如果 `_INDEX.md` 与旧 README 或旧 skill 冲突，以现行根索引和声明为唯一标准的规范为准，并报告陈旧文件。

## 1. 建立输入清单

列出全部来源及其稳定身份：

- 仓库相对路径或 URL
- 文件、目录、源码仓库或网页等来源类型
- SHA-256 内容 hash；源码还需 branch/commit
- 来源对应的项目、客户、版本和日期（能确定时）

扫描目录时忽略知识库自身的生成目录和附件缓存，避免把输出再次当输入。发现来源删除或重命名时只标记，不自动删除历史知识。

## 2. 预处理与分块

预处理不得改变 Raw：

- 统一读取编码和换行，仅用于本次分析
- 保留标题、时间戳、表格、代码位置、日志顺序和说话人等证据锚点
- 删除噪声只作用于临时表示；任何可能改变语义的信息都必须保留

优先按现有标题、议题、需求点、故障阶段、协议章节或源码模块分块。每个 chunk 记录来源定位；不要只生成不可回溯的 `CHK-001`。

## 3. 提取与证据分级

对每个候选知识项记录：

- 类型与主题
- 项目、平台、客户、版本
- 关联模块、协议、状态机和硬件
- 结论、原因、约束、风险、边界与待确认项
- 来源定位
- 证据等级：明确事实 / 归纳结论 / 待确认推断

遇到以下情况不得补全为确定事实：

- 会议只有讨论、没有最终决策
- Bug 只有现象、没有根因证据
- 需求缺少边界或验收口径
- 源码行为与需求意图不一致
- 不同版本或客户规则冲突

## 4. 路由和模板选择

先判断知识归属，再判断知识类型，最后确定文件位置。

1. 查根索引确认顶层区域。
2. 查项目或功能 `_INDEX.md`，复用已有功能目录和术语。
3. 查命名规范确定目录名和文件名。
4. 读取 `模板/` 中对应模板，保持 Frontmatter 与章节结构。
5. 没有模板或类型未被规范定义时，不自创新 schema；先输出拟议结构并请求确认。

AI 草稿通常直接进入真实目标目录并以 Frontmatter 表示 draft。只有根索引或现行规范明确要求时，才使用集中式 `AI/DraftWiki/`。

## 5. 去重和冲突预检

在写文件前搜索：

- 目标项目、功能和知识类型目录
- 平台、通用、客户区的同主题知识
- `status: active` 与 `status: draft` 文档
- 最近一级 `_INDEX.md`、全库索引、决策索引和待审核入口
- 编译索引中的历史输出

比较作用域后分类：

| 结果 | 处理 |
|---|---|
| 无已有主题 | 新建 draft |
| 同结论、同作用域 | 复用或最小合并，补充来源 |
| 信息互补 | 生成针对现有 draft 的最小 diff |
| active 需要更新 | 生成修订草稿或受控 diff，等待人工审核 |
| 结论冲突 | 不写入结论性正文，输出冲突报告等待裁决 |
| 客户/版本不一致 | 分层或版本化，不做通用合并 |

冲突报告默认在对话或工作报告中给出。只有库内已有对应类型/模板或用户确认后，才新增冲突文档。

## 6. 生成知识草稿

生成时：

1. 复制并填充库内模板，不复制本技能中的示例。
2. 按 Frontmatter 规范使用允许字段和强制顺序。
3. AI 新文档固定使用 `status: draft` 与 `reviewed_by: AI-draft`。
4. 用正文表达来源、依据、未知项和冲突；不要新增未获规范许可的 Frontmatter 字段。
5. 添加与需求、详设、决策、Bug、协议、项目索引等真实文档的双链。
6. 只修改目标文档需要变化的部分，避免机械重排整篇文件。

## 7. 更新导航和追踪

按当前库规则同步：

- 最近一级项目或功能 `_INDEX.md`
- 根 `_INDEX.md`（仅当新增项目/主要入口确有需要）
- `_DECISIONS.md`（仅决策且现行规则要求）
- `PENDING-REVIEW.md` 或当前待审核入口
- `AI/Index/compile_index.json`

索引只做导航和一句话摘要，不复制正文。编译追踪 schema 见 `compile-index.md`。

## 8. 校验

至少执行以下只读或本地校验：

1. 解析所有改动 Markdown 的 Frontmatter。
2. 检查必填字段、字段顺序、允许字段、日期格式和非空 tags。
3. 检查新增或变更的 `[[双链]]` 目标和标题锚点。
4. 检查模板占位符、空章节、无证据结论和客户/版本串层。
5. 解析编译索引，复算本地来源 hash，确认输出文件存在。
6. 检查 `git diff --check`、`git status` 和范围内 diff。

不要通过重写或清理无关文件来让校验通过。

## 9. 交付与提交门禁

先向用户报告：

- 新建和更新的文件
- 复用或合并的知识
- 冲突与待确认问题
- 校验通过项和未通过项
- 工作树中与本次无关的既有修改

随后展示本地 diff 或可点击文件。只有用户明确批准后，才按仓库规范执行 commit、push、MR、评审回复或合并；对其中一个动作的批准不自动授权后续动作。
