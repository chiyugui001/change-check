# Knowledge Compiler

把原始材料转化为可追溯、可评审、可长期维护的工程知识。重点是形成稳定结论、设计原因、约束、风险和关系，不是改写或复制原文。

## 权威来源

每次执行都从目标知识库重新加载契约，禁止把本技能中的示例当成知识库 schema。

按以下优先级处理冲突：

1. 用户本次明确要求和目标仓库中的 `AGENTS.md`
2. 根索引 `_INDEX.md`、根 `README.md` 与仓库身份说明
3. `知识库规范/` 下的现行规范，尤其是 Frontmatter、命名、双链、AI 使用和 Git 版本迭代规范
4. `模板/` 下对应知识类型的模板
5. 项目或功能目录中的 `_INDEX.md`、已审核文档和现有目录结构
6. 本技能的流程参考文件

如果库内规范互相冲突，以明确声明为“唯一标准”的现行规范为准，并在结果中报告冲突；不得自行拼出第三套规则。

目标库的身份和目录由实际内容决定，不能因为路径名包含 `obsidian` 就假定它仍采用旧的个人库英文目录。当前库若使用 `项目/`、`平台/`、`通用/`、`客户/`，就不得写入不存在的 `Projects/`、`Platforms/`、`Common/`、`Wiki/` 或 `AI/DraftWiki/`。

## 必须遵守的边界

- Raw 是证据层。预处理只在内存或临时工作区进行，不静默修改、清洗或删除原始文件。
- AI 新建或实质改写的知识默认是 `status: draft`、`reviewed_by: AI-draft`；不得自行升级为 `active`。
- Frontmatter 只使用当前库规范允许的字段、顺序和取值。编译追踪信息优先放在 `AI/Index/compile_index.json`，不得为方便追踪而污染文档 schema。
- 使用目标库现有模板，不在技能中维护第二套正文模板。
- 不覆盖已审核知识。发现同主题文档时先比较并给出合并方案；结论冲突、客户作用域不明或版本无法判定时停止写入该知识项，交由人工裁决。
- 不把不同客户、版本、项目或平台的规则合并成无作用域的通用结论。
- 有关联的知识必须建立双链，并更新最近一级 `_INDEX.md`；AI 草稿还应进入库内现行的待审核入口。
- 默认只完成本地修改、校验和 diff。除非用户明确批准，不得 commit、push、创建 MR、回复评审或合并。
- 工作树已有修改属于用户。只修改本次范围内的文件，不清理、不回退、不顺手格式化无关内容。

## 执行入口

1. 先定位知识库根目录并读取上述权威来源。
2. 判断请求模式：
   - **评估/预览**：只分析、路由和给出拟产物，不写文件。
   - **编译/整理/修改**：生成或更新本地 draft，并展示校验结果和 diff。
   - **提交/发布**：仅在用户明确授权对应动作后执行仓库规定的 feature 分支与 MR 流程。
3. 执行编译流水线。完整步骤见 [references/workflow.md](references/workflow.md)。
4. 选择文档结构时读取 [references/templates.md](references/templates.md)。
5. 增量编译或更新索引时读取 [references/compile-index.md](references/compile-index.md)。

## 输入与作用域

支持单文件、目录、多个相关材料、源码快照或可追溯 URL。先记录来源身份，再提取知识：

- 文件：仓库相对路径和内容 hash
- 目录或源码：仓库/目录、分支、commit 或其他稳定 revision
- URL：原始 URL、可获取的版本信息和抓取日期
- 多来源：作为一个编译单元记录全部来源，不能只保留最后一个来源

根据内容路由，而不是根据输入文件夹机械路由：

- 单项目特有知识 → 当前库的项目区
- 多项目稳定共性 → 当前库的通用区
- 产品平台共性 → 当前库的平台区
- 客户覆盖或定制规则 → 当前库的客户区

无法可靠判断项目、客户、版本或目标功能目录时，在写文件前询问用户；可以继续完成不依赖该选择的提取和冲突分析。

## 知识提取要求

从证据中按需提取：Requirement、Decision、Technical Spec、Bug、Protocol、State Machine、Risk、Module、Hardware、Customer 和 Version。

每条结论都应能回溯到来源。区分：

- 来源明确陈述的事实
- 从多个证据归纳出的结论
- 需要工程师确认的推断或缺口

不得把推断写成已确认事实。Decision 要保留为什么选择和为什么不选；Bug 要保留现象、触发条件、根因证据、修复理由和防复发；详设要明确接口、状态、边界、硬件约束和与源码版本的关系。

## 去重与冲突

去重范围必须覆盖实际知识目录、现有 draft、待审核索引和相关 `_INDEX.md`，不能只扫描一个固定的 `Wiki/` 目录。

比较时至少考虑：主题、模块、项目、客户、版本、状态、结论和来源。

- 相同作用域且结论一致：提出复用或合并方案，保留全部来源。
- 相同主题但信息互补：基于现有文档生成最小合并 diff。
- 结论矛盾：报告双方证据、状态、版本和客户作用域，不自动合并。
- 旧文档为 `active`：只能提出修订草稿，不得静默覆盖或降级。

## 完成标准

本地编译完成前必须验证：

- 目标路径符合根索引和命名规范
- Frontmatter 必填字段、字段顺序、取值和标签符合现行规范
- 正文来自库内对应模板，章节没有遗留占位符
- 关键结论有来源或明确标注为待确认
- 项目/客户/版本作用域没有串层
- 双链目标和标题锚点可解析；相关 `_INDEX.md` 与待审核入口已同步
- `compile_index.json` 可解析、来源 hash 正确、输出路径存在
- 未覆盖 active 文档，未改动 Raw，未混入无关工作树修改
- diff 无明显格式错误，并向用户说明生成、更新、冲突和待确认项

若任何强制校验失败，保留可审查的本地结果但明确标记未完成，不得提交或宣称编译成功。
