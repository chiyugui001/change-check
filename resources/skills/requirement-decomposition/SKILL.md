# 需求拆解

把原始需求转成可供产品、研发和测试共同审核的需求文档。重点不是扩写原文，而是明确本模块要做什么、不做什么、依赖谁、如何验收，以及哪些问题仍不能进入实现。

## 与知识编译底座的关系

向工程知识库写入或更新文档前，先加载并遵循已安装的 `knowledge-compiler` 技能。它负责运行时发现知识库契约、Raw、索引、工作树和提交门禁；本技能只补充需求拆解语义。两者冲突时，用户本次明确要求和目标知识库当前规范优先。

## 执行模式

- **分析/预览**：只输出证据矩阵、边界、冲突和拟写结构，不修改文件。
- **拆解/迁移**：建立或复用 Raw 证据，生成需求草稿并同步当前知识库要求的导航和审核入口。
- **评审修订**：按评审意见做最小一致性修改；已确认项写回正文、参数和验收，随即从待确认问题移除。

## 核心工作流

执行前完整读取 [references/method.md](references/method.md)，并按其中的证据分级、模块归属、章节职责和质量门禁工作。任务涉及风险章节、参数组合限制、状态恢复或用户要求发散风险时，继续完整读取 [references/risk-analysis.md](references/risk-analysis.md)。

1. 发现当前模板、Frontmatter、目录、索引和 Git 边界，不复用旧会话中的 schema。
2. 建立全部来源清单和稳定定位；Raw 保留原文、版本与缺口，不把清洗结果覆盖回证据层。
3. 将内容分为来源事实、评审确认、推导建议、待确认缺口和关联模块信息。
4. 先确定本需求的责任模块，再写场景、功能、参数、依赖、风险和验收；关联模块的内部规则留给其自己的需求。
5. 写作或精简前建立“来源/评审确认点 → 正文唯一落点 → 边界或验收覆盖”的需求覆盖映射；正文每删减或合并一项，都要先证明其完整语义已保留在明确位置。
6. 所有待确认问题必须具体、可回答、属于当前模块。风险只记录规则、参数或能力边界明确后仍存在的负面影响；不能只改写来源已提出的问题，还要按风险分析参考检查合法参数组合、状态生命周期、输入与硬件能力、依赖失效及极值场景。确认答案会消除的问题仍属于待确认项，不得写成风险。
7. 会改变用户可见行为、参数、交互、状态流转、恢复规则、仲裁结果或验收预期的待确认项一律列为 P0，在需求与测试冻结前确认。P1 只用于不改变外部行为和验收结果的详设选择；需求文档没有这类问题时不保留 P1 分组。
8. 按目标库模板生成最小 diff，保持人工修改；默认只本地修改和校验，不提交、不发布。

## 语义无损精简（硬性门禁）

“简洁”只允许通过删除重复背景、证据转述、实现过程、历史改造说明和跨章节复述实现，不能通过减少产品规则实现。若完整性与篇幅发生冲突，先保留完整语义，再通过章节归位、表格合并和短句改写压缩表达。

以下已确认内容不得因“简化”“对齐风格”或“避免重复”而删除、模糊或降级为待确认：

- 功能启用方式、显示条件、默认值和有效输入。
- 计算公式、阈值偏移、比较符号及等号归属。
- 触发、保持、解除、切换和重入条件。
- 计时起点、计时单位、连续性、`0` 值语义和立即生效规则。
- 并行功能或状态之间的独立、互斥、优先级和联动关系。
- 事件类型、业务结果、输出对象和用户可观察结果。
- 参数范围、精度、非法值、上电、重启、配置修改和异常规则中已经确认的部分。
- 能直接转成测试的正常、边界、切换和异常验收要点。

允许消除文字重复，但不允许消除需求覆盖。完成前必须逐项回查需求覆盖映射：每个来源事实或评审确认点都有正文唯一落点；涉及边界或状态迁移时有对应边界说明；具备外部可观察结果时有对应验收项。任一已确认点无落点时，不得宣称精简或评审完成。

若项目明确指定一份已审核需求作为表达范本，只复用其章节职责、功能拆分粒度和文字密度，不复制其业务事实。项目专用技能可以进一步把该范本设为强制基线。

## 不可破坏的边界

- 不把设计建议、代码结构、协议字段或历史平台行为写成原始需求。
- 不为填满模板而编造默认值、范围、异常处理或验收数字。
- 不在正文重复 Frontmatter 已表达的草稿/审核状态。
- 不把关联模块的参数、算法、停留时间、仲裁或恢复策略复制进当前模块。
- 需求描述要具体、清晰，站在研发人员视角应能快速理解实际行为，不依赖模糊术语或额外猜测。例如，不写“设备不上报历史值，不要求平台差异合并”，应写“设备不上报历史配置或配置变更记录，仅上报当前生效配置”。
- 不静默覆盖 `active` 文档；先比较人工版本并生成最小修订。
- 不因一次评审样例建立普遍规则；只沉淀能跨功能复用的判断方法。
- 不把“删除重复”理解为同时删除正文规则和验收覆盖；正文负责定义行为，验收负责定义可观察判据，两者职责不同。

## 完成标准

除 `knowledge-compiler` 的知识库校验外，还必须确认：需求覆盖映射无遗漏；每个功能点能回溯到来源或评审确认；所有已确认公式、边界、时序、状态、交互和验收语义仍有明确落点；模块边界没有串层；参数只包含本模块所有；待确认项没有抽象术语；每条风险都有已确认依据、合法触发条件和可观察后果，并已落实必要的验收覆盖；验收项能够直接转成测试；评审已确认的问题不再残留为风险或待确认项。
