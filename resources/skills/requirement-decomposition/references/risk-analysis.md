# 需求风险分析方法

仅在编写或评审需求风险、检查参数组合限制、状态恢复，或用户要求发散风险时读取。本方法用于发现已确认规则仍会带来的负面影响，并把未决行为正确分流到 P0；不用于替代安全、可靠性或详细设计专项分析。

## 1. 先判定内容属于哪里

对每个候选问题依次判断：

1. 相关业务规则、参数范围或能力边界是否已经由来源或评审确认？
2. 触发条件是否属于合法配置、正常状态组合或设备确实可能遇到的故障？
3. 即使规则已经确认，负面影响是否仍然存在、只能缓解或需要明确接受？

按答案分流：

| 情况 | 归属 |
|---|---|
| 三项均为“是” | 风险 |
| 不同答案会改变用户行为、状态、恢复或验收 | P0 待确认 |
| 只影响内部实现且不改变外部行为 | 详设 |
| 只是输入范围、状态切换或异常事实，没有明确负面后果 | 边界条件 |
| 属于关联模块内部问题，且不会直接改变本模块结果 | 移交关联模块 |

产品或用户已经给出明确回复时，先把回复写回功能规则和验收，再判断该规则是否仍伴随风险。不得继续写“请产品评估是否接受”；只有负面影响本身尚未被知情接受且确实需要发布决策时，才保留接受动作。

## 2. 建立最小行为模型

不要直接对着“风险”标题发散词语。先从正文提取：

- 输入：数据来源、有效性、精度、更新或采集周期。
- 配置：开关、枚举、阈值、持续时间、超时、上下限和默认值。
- 状态：禁用、监测、触发、保持、解除、恢复及高优先级覆盖状态。
- 输出：用户可见状态、控制动作和本模块强关联的业务通知。
- 生命周期事件：启停、运行中改配置、来源或模式切换、数据失效与恢复、手动操作、重启和掉电。
- 依赖：上游输入可能迟到、错误、卡滞或无法区分的情况，以及下游动作对本模块目标的反作用。

模型只需覆盖能改变本模块结果的对象，不展开关联模块的内部算法、协议重试或存储实现。

## 3. 按维度做组合检查

### 3.1 参数与时间尺度

优先组合共享同一判断或结果的参数，不机械遍历全部笛卡尔积：

- 采集或控制周期与判断窗口、持续时间、超时之间是否匹配。
- 阈值与传感器分辨率、精度、噪声或最小可观测变化是否匹配。
- 最小值、默认值、最大值和相邻边界是否会让功能失效、响应过慢或影响被放大。
- 恢复时间是否短于重新观测或重新触发所需时间。
- 两个参数单独合法时，组合后是否仍能达到目标。

### 3.2 状态生命周期

沿“进入—保持—解除—恢复”检查：

- 运行中禁用功能、切换模式或来源、修改阈值与时间参数时，当前状态和计时如何处理。
- 输入失效后恢复、来源切换或校准变化时，旧基线和历史状态是否会污染新判断。
- 手动解除后触发条件仍存在时，是立即重触发、重新累计，还是等待条件恢复。
- 更高优先级保护覆盖当前动作后，退出保护时恢复哪个状态。
- 重启或掉电后，告警、计时、剩余持续时间和配置是否恢复。

缺少规则时写成具体 P0，不得把“可能状态错乱”直接列为风险。

### 3.3 输入、观测与硬件能力

检查：

- 检测量是否只是业务目标的间接证据，从而天然存在误报或漏报。
- 数据无效、超时、缺失或更新过慢时是否形成检测盲区。
- 硬件是否能区分真实业务事件与断线、卡滞、抖动或传感器故障。
- 当前能力是否能观察并验收需求声称的时间、精度或状态。

能力限制已经明确且无法由需求选择消除时写风险；判定方法、故障呈现或恢复动作尚未决定时写 P0。

### 3.4 依赖与优先级

检查上游错误状态是否会直接驱动本模块动作，以及高优先级安全规则是否会削弱本模块目标。已确认的安全优先级造成能耗、舒适性或响应折损时，属于可记录风险；优先级本身未确认时属于 P0。

发送次数、失败重试、超时、离线补发和重复抑制等统一通信问题不在每个模块重复列风险，除非通信结果会直接改变本模块状态或业务动作。

## 4. 写成可审核的风险

每条风险至少包含：

- 风险名称：指出限制或失效模式，不使用“规则不明确”“需要确认”。
- 触发条件：给出合法配置、状态组合、输入或故障条件。
- 可观察后果：说明用户、设备控制、能耗、舒适性或验收会看到什么。
- 处理方式：记录规避、缓解、测试覆盖或已接受的权衡；不能暗中增加新需求。

处理方式如果要求收紧参数范围、改变算法或增加新的故障诊断能力，这本身是需求变更建议。未获确认前应进入 P0 或评审建议，不能写成既定缓解措施。

## 5. 回写正文与验收

- 已确认规则：同步更新功能详情、参数、边界和验收，并删除旧待确认问题。
- 已确认规则仍有负面影响：保留风险，但不再要求重复确认同一个规则。
- 未决行为：只进入 P0；风险表不保留同义项。
- 风险需要测试控制：在验收中覆盖代表性组合、参数上下限、干扰场景或恢复路径。
- 索引或审核摘要曾写“风险是否接受”时，评审闭环后同步改为已知风险或真正剩余的 P0。

## 6. 快速示例

- 已确认始终比较相邻采样值，但采样周期可大于判定尺度：尺度失配造成误报或漏报是风险，不再把比较规则列为待确认。
- 数据来源切换后是否沿用旧比较基线没有答案：不同选择会改变触发结果，应列为 P0。
- 已确认安全保护优先于节能动作：安全动作造成节能效果下降是已知风险，优先级本身不再待确认。
- 普通模块只要求上报业务状态：网络重试和离线补发属于统一上报规则，不在该模块重复发散风险。

## 7. 完成检查

- 每条风险都有已确认依据、合法触发条件和可观察后果。
- 已确认的产品回复没有继续残留为待确认或“请评估是否接受”。
- 参数周期、判断窗口、阈值、超时和控制周期至少完成相关组合检查。
- 启停、运行中改配置、来源切换、输入恢复、手动操作、优先级覆盖和重启均已检查；缺项有明确的不适用理由。
- 上游能力限制只保留对本模块的直接影响，没有复制关联模块的内部需求。
- 风险与 P0 不重复，缓解措施没有偷偷冻结新需求。
- 风险对应的边界或验收覆盖已经同步，索引摘要没有旧口径。
