# 需求拆解方法

仅在执行需求拆解、迁移或评审修订时读取。

## 1. 先建立证据矩阵

对每个候选需求点记录来源定位、作用域、结论和证据类型：

| 类型 | 含义 | 写入规则 |
|---|---|---|
| 来源事实 | 原始资料明确陈述 | 可写入正文，并保留行、记录、章节或版本定位 |
| 评审确认 | 产品或用户在评审中明确确认 | 更新正文、参数和验收；从待确认项移除 |
| 推导建议 | 为实现完整性提出的设计方案 | 不得写成需求事实；按需进入设计依据或详设建议 |
| 待确认缺口 | 不同选择会改变产品行为、协议或测试 | 写成具体问题，列明触发场景、备选口径和影响 |
| 关联模块信息 | 由其他模块拥有的参数或算法 | 当前需求只保留输入输出或依赖关系，详细内容移交所属模块 |

多来源合并时保留各自权威范围。例如产品需求表决定目标和范围，参数表决定展示名、值域、默认值和显示条件；来源冲突时不按“表更新得较晚”自动裁决。

## 2. 决定模块所有权

对每条信息回答：谁配置、谁产生状态、谁消费状态、谁决定最终业务动作、谁能独立验收。

- 当前模块拥有输入解释、状态输出或直接动作时，写入功能详情。
- 当前模块只向下游提供状态时，不复制下游告警、控制、恢复或计时规则。
- 从研发人员视角检查需求描述是否具体、清晰，能否快速理解实际行为而不需要额外追问术语含义。例如，不写“设备不上报历史值，不要求平台差异合并”，应写“设备不上报历史配置或配置变更记录，仅上报当前生效配置”。
- 跨模块关系写入影响模块或依赖关系；关联模块的参数放入其自身需求。
- 当前模板若规定“影响模块”为代码模块，就按代码模块写；用户或项目规范明确采用产品功能模块时，遵循其明确口径。不要把实现职责清单冒充产品模块。
- 依赖关系表达哪些需求或模块必须先完成、以及本需求会解锁或影响谁。硬件电平、接口签名、持久化布局等技术依赖进入详设。

## 3. 各章节只承担一种职责

| 章节 | 应回答 | 避免 |
|---|---|---|
| 背景 | 为什么需要、来源与版本范围 | 功能细节和实现方案 |
| 目标 | 用户或系统最终获得什么能力 | 任务列表 |
| 范围边界 | 本模块包含和明确不包含什么 | 把关联模块完整需求抄进“不包含” |
| 用户场景 | 谁在什么条件下做什么并得到什么 | 只写内部函数调用 |
| 影响模块 | 哪些模块需要配合或受影响 | GPIO、队列、Flash 等未冻结实现职责 |
| 功能详情 | 当前模块的输入、规则、输出和异常 | 关联模块算法、未确认默认值 |
| 参数 | 当前模块拥有的名称、显示条件、值域、默认值 | 关联模块参数、猜测字段名或 C 变量名 |
| 依赖关系 | 前置模块/需求和后置影响 | 技术接口清单 |
| 设计依据 | 已确认的选择理由 | 把个人建议包装成产品决定 |
| 边界条件 | 输入边界、状态切换、异常情形 | 未量化的泛泛风险 |
| 风险 | 规则明确后仍存在的已知限制、触发条件及后果 | 把未决规则、参数缺口或待选择方案写成风险 |
| 验收标准 | 可观察、可测试的输入和结果 | “功能正常”“兼容良好”等空话 |

不要新增模板没有要求的“来源定位”“AI 说明”等章节，除非当前知识库规范或用户明确要求。`source` 和状态优先按 Frontmatter 规范表达。

风险不是待确认问题的改写。只有需求规则、合法参数范围和能力边界已经明确，负面影响仍无法完全规避或需要明确接受时，才写入风险。若给出一个产品选择就能消除该问题，应列为待确认项；确认完成后删除，不保留为风险。

任务涉及风险编写、风险评审、参数组合限制、状态恢复或发散风险时，完整读取 [risk-analysis.md](risk-analysis.md)，按其中的准入判定、分析维度和回写规则执行。

### 3.1 用章节归位实现精简

精简前先建立一份工作用覆盖映射；除非目标模板要求，否则不必把它写入最终需求：

| 来源或评审确认点 | 必须保留的完整语义 | 正文唯一落点 | 边界/验收覆盖 | 处理结果 |
|---|---|---|---|---|
| 稳定定位 | 触发、判断、状态、输出、参数或时序 | 对应功能或参数小节 | 对应边界与可观察判据 | 保留 / 合并 / 转 P0 |

按以下顺序压缩文字：

1. 删除证据推导、历史改造过程、设计实现和无业务含义的说明。
2. 将属于参数、边界、风险或验收的内容归入各自章节，正文不跨章节重复整段规则。
3. 合并同一能力下句式相同的规则，优先使用短列表或紧凑表格，但保留每个条件与结果。
4. 用户场景只说明角色、配置或前提、操作以及业务结果；不重复功能详情的公式、参数表和完整状态迁移。
5. 功能详情按能力点直接说明输入、规则和输出；不写来源争议、代码现状、改造过程或验收口号。
6. 验收标准只写可设置的前提、输入或操作和可观察结果；它不是背景复述，但必须覆盖正文的可测行为。

任何合并都必须保持比较符号、等号归属、数值偏移、计时起点与 `0` 值语义、触发/保持/解除条件、状态联动、默认值、显示条件和异常结果。若一句短写会产生两种合理解释，就不能视为合格的“简洁”。

## 4. 参数与冲突处理

每个参数至少确认：展示名称、所属模块、显示条件、取值范围、默认值、来源定位。某一项缺失就明确留空或标为待确认。

- 同义参数先查术语表和现有 `active` 文档，不自行创造别名。
- 参数表与需求表不一致时，列出冲突和各自定位，不拼成第三种口径。
- 评审补充了参数规则时，标明其属于评审确认，不伪称来自原表。
- 关联模块参数不能为了“说明完整”放进本模块参数表。

## 5. 待确认问题质量

合格问题应让负责人能直接回答。例如：

> 当设备上电时输入已经有效，是立即产生一次事件，还是只处理上电后的边沿变化？两种选择会影响首次状态和重启验收。

不合格问题包括：“如何仲裁”“稳定 ID 是什么”“异常怎么处理”。应展开为具体对象、触发时序、备选结果和影响。

待确认项按影响分级：只要不同答案会改变用户可见行为、配置含义、交互、状态流转、恢复、仲裁或测试预期，就属于需求问题，列为 P0 并在需求与测试冻结前确认。P1 仅保留不改变外部行为和验收结果的详设选择；这类问题应优先移交详设，需求文档没有时不设置 P1 分组。

以下情况不再保留为待确认：

- 评审已经给出明确答案。
- 该行为显然由已有确定规则唯一决定，重复描述没有验收价值。
- 当前硬件无法观察或实现，只能作为已知风险报备。
- 问题属于其他模块内部实现，应移交对应模块。

## 6. 评审闭环

每条评审意见都检查所有受影响位置：场景、影响模块、功能详情、参数、设计依据、边界、风险、验收和待确认列表。

- 确认新规则：更新所有相关章节，删除旧的缺口、风险和相反表述。
- 收紧模块边界：删除关联模块细节，但保留必要的输入输出或依赖。
- 删除冗余：同时删除正文和验收中的重复规则。
- 改写术语：用业务含义替代无法直接理解的技术简称。
- 人工已审核的 `active` 文档只做评审授权范围内的最小修改，不重排全文。

## 7. 质量门禁

完成前逐项核对：

- 来源读取完整，没有把分页、截断或局部范围当全量。
- 原始证据与结构化需求分层，Raw 未被清洗覆盖。
- 每条已确认需求至少有来源事实或评审确认。
- 精简前后的需求覆盖映射一致，所有已确认点都有正文唯一落点；涉及边界、迁移或外部结果时同时具备相应边界或验收覆盖。
- 没有为缩短篇幅删除公式、比较符号、等号归属、数值偏移、计时与 `0` 值语义、状态切换、默认值、交互限制或异常结果。
- 未确认信息没有以陈述句、默认值或验收项形式冻结。
- 当前模块与关联模块的参数、算法和责任没有混写。
- 待确认问题均具体且仍未解决，编号连续。
- 验收覆盖正常、异常和边界路径，并能直接观察结果。
- 模板占位符、正文草稿声明、无效双链和多余章节已经清理。
- 索引、审核入口和编译追踪只按目标知识库当前规则更新。
