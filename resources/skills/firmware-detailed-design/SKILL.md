# 固件详设编写

产出可实现、可评审、可追溯的固件详设。详设只描述目标设计和稳定契约，是后续实现的权威输入；现有源码仅用于核对业务逻辑、模块边界、平台约束和可实现性，不在正式详设中呈现现状、差异或改造过程。

## 授权边界

- 用户只要求解释或复核时，以只读检查和问题报告为主；没有明确要求修改时不写文件。
- 用户要求编写或修改详设时，只修改知识库范围内的文档；代码实现需要另行授权。
- 保留工作区已有改动，不覆盖、不回退与当前任务无关的文件。
- 未经明确授权不提交；提交、推送和创建合并请求分别视为独立授权。
- AI 新建或修改的知识默认保持待审核状态，审核字段和生命周期以当前知识库规范为准。
- 用户只要求诊断或修正一份详设的 Frontmatter 时，默认范围仅为该详设及其详设模板/校验材料；不得顺带修改需求、Raw、索引或其他文档的 Frontmatter，除非用户扩大范围。

## 运行时发现上下文

不要把盘符、用户目录、仓库名、分支或模板路径写死在技能中。

1. 根据用户措辞确定个人库、团队库或其他目标库；无法唯一判断时先询问。
2. 从当前工作区、仓库配置、知识库入口或显式链接中定位知识库根和目标项目库。
3. 先读项目 `_INDEX.md`、当前库的知识库规范、`详设` 模板和一个已审核示例。库内规范和模板优先于本技能的通用建议。
4. 读取相关需求、决策、协议、关联模块详设、待审核清单及硬件资料；不要只依赖聊天记录或 Raw。
5. 定位源码仓库、当前分支和提交。若项目存在 `graphify-out/graph.json`，先查询图谱确定调用链和依赖，再按需读取具体源码；图谱也可能位于仓库上层或关联工作区，应在有限的相关路径中搜索后再判断不存在。
6. 从图谱和当前源码整理项目术语表，至少包括模块、任务、执行上下文、函数、事件和类型。图谱可能来自历史提交，最终名称和调用关系必须回到锁定源码确认。
7. 为每个关键结论记录证据来源，并区分已确认要求、源码事实、设计选择和待确认事项。

## 编写流程

### 1. 冻结范围与职责边界

- 用一句话定义模块解决的问题，以及它向上游接收什么、向下游输出什么。
- 明确本模块负责和不负责的事项。模块只描述自己产生的状态、动作请求或引用；下游如何执行由下游详设定义。
- 模块概述只保留对应需求范围、依赖关系和职责边界，不单设“设计目标”小节。依赖关系图作为第 1.2 小节的唯一关系图，明确区分上游输入与请求、本模块和下游使用方；通知分发与查询依赖按实际存在关系画出。工程结果和关键约束分别写入对应的接口、逻辑、时序、配置或风险章节，不在概述中重复汇总。
- 按业务职责拆文档，不按源码文件数量拆分。
- 源码支撑的详设需要建立模块文件组成清单。只列本模块直接维护、且职责落在当前边界内的源文件和头文件；调用方、通知分发、参数管理、协议解析、板级驱动和下游消费者等协作文件不得因出现在调用链中而计入本模块。文件归属以职责边界为准，不以“被调用”或“参与同一业务链路”为准。
- 模块组成作为“模块概述与职责边界”下的 1.4 小节，紧随职责边界列出模块文件及职责，不再单独设置“模块组成”章节，也不混入处理流程或外部协作文件。

### 1.1 上下游契约边界

- 模块详设以自身职责为边界：明确接收哪些上游事件、输入什么数据、何时处理，以及产生哪些业务事实或结果。
- 输入契约写清发布方、触发条件、载荷、取值、有效期、执行上下文及失败处理；内部回调只说明如何承接输入，不列为外部可调用接口。
- 输出事件使用本模块的业务语义。可由多个模块消费的消息采用通用事件与稳定载荷，外部模块按需订阅，不将具体消费者或其业务动作固化在本模块中。
- 消费者是否上报、同步其他设备、构造报文或执行重试，归消费者详设；本模块不替下游定义业务步骤，不以订阅方联网或连接状态决定是否发布业务事实。
- 仍须定义消息发布时机、顺序、复制与有效期、投递失败处理等必要契约；这些接收约束不能因“下游自行处理”而省略。
- 事件概览只列外部实际使用的事件名、方向、发布方、接收方和用途；载荷值、字段与发送示例放入详细定义，内部转换枚举和辅助回调不得冒充对外事件。
- 职责表和时序图止于稳定接口或消息交付边界，不展开消费者内部流程。已有直接调用的稳定契约仍可保留，不能机械改成广播或删除真实依赖。
- 本身负责上报、协议或同步的模块按其职责描述处理行为；判断是否越界应依据模块责任，而非仅因出现某个下游名称。

**脚本校验**：

- 修改前后运行 [scripts/validate_detailed_design_boundaries.py](scripts/validate_detailed_design_boundaries.py)：`python <脚本路径> <详设路径>`，支持多个文件。
- 自动检查概览列数、边界字段、名称列载荷混入及已知内部符号；具体消费者绑定、通信语义事件名和强制下游业务措辞作为 `REVIEW` 候选项。
- `--internal-symbol <符号>` 可补充已确认内部符号，`--consumer-token <标识>` 可补充本次消费者标识；均可重复。标识随本次检查传入，不写入通用脚本。
- `--json` 输出文件、行号、规则编号和严重程度。退出码 `0` 表示未命中，`1` 表示存在检查项，`2` 表示参数或文件读取错误。
- 脚本只读；`ERROR` 修正后重跑，`REVIEW` 结合职责和证据逐项判断并说明处理。不得仅凭关键字自动删改接口，也不得以脚本通过代替完整语义复核。
- 扫描范围为 Markdown 概览表和正文；围栏代码与图不按正文措辞检查，仅提取 C 围栏中的内部声明。多行语义、消息完整性和图中边界须人工复核。

### 2. 建立目标设计

- 正文统一以设计完成态描述目标架构、接口、事件、状态和约束，允许调整当前代码结构。
- 正文中的设计对象先使用能表达职责或业务含义的通用名称，不得只用文件内变量名、静态对象名或数组名代替设计概念。确需建立源码映射时，采用“通用名称（实际变量名：`xxx`）”或单独增加“实际变量名”列；变量名不能脱离通用说明单独出现。
- 表格中的发布方、接收方、所有者、组件、依赖对象、运行位置和传递方式等角色列，也必须先说明通用角色或职责，再在括号中标注实际函数名、模块名、任务名、接口名或类型名；不得只填一个 C 标识符。函数、类型和事件等稳定标识符仅在接口名称、函数原型、类型定义和事件定义中可以直接使用。
- 设计时明确每份实际数据由哪个模块维护。区分模块内部记录、调用方缓冲区、发送方原消息和队列副本，不因类型相同而共用归属或生命周期结论；只有存在多个可能维护方时才在正文写明维护责任，发生所有权转移时说明具体转移条件，不把副本持有方当成原对象的共同所有者。
- 正式详设不记录“当前未实现”“已有部分实现”“现有链路未闭环”等实现进度，也不包含现状对比、文件改造清单、迁移步骤或实施顺序。
- 现有源码只作为设计输入，用于复用合理逻辑、核对平台事实和识别设计约束；不得让过渡实现结构污染目标契约。
- 用户明确要求源码现状审计、差异分析或代码改造计划时，另行输出独立核对文档，不作为详设正文、小节或附录。
- 未冻结行为标为“建议设计，待评审冻结”，并写清影响与确认方式，不把推测写成确定行为。

### 2.1 精简长文字并分点

- 纯文字说明默认单行不超过 120 个可见字符、连续段落不超过 200 个；当前库明确规定其他阈值时按库规则传参。
- 超限时先删重复内容，再以 `- ` 小圆点列表逐项分行；列表前留空行，每项一个要点且整项不超过单行阈值。
- 源码换行仍按同段或同项累计，不通过空行切段或添加无关图表规避超限；保留条件、动作、时机、异常和结果，不拆断标识符。
- 汉字、字母、数字和标点各计 1；忽略空白、格式标记和链接地址，保留链接显示文字与行内代码标识符。
- 排除 Frontmatter、HTML 注释、标题、Markdown 表格、图片和代码块（含 Mermaid）；相邻图表不豁免文字检查，也不逐句复述图表。
- 写入前后运行 [scripts/validate_detailed_design_prose.py](scripts/validate_detailed_design_prose.py)：`python <脚本路径> <详设路径>`，可传多个文件。
- `--line-limit` 和 `--paragraph-limit` 可指定库内阈值；退出码 0 表示长度通过，1 表示超限，2 表示参数或读取错误。
- 脚本只读，输出文件、行号、规则和长度；人工复核重复语义与要点拆分，不把长度通过等同于内容已精简。
- 局部修改修正本次涉及的说明块并报告历史超限，不擅自重写全文；全篇编写或修订须修正全文超限。

### 2.2 内容归属与重复校验

- 按当前模板的章节用途确定内容归属，同一事实只保留一处完整定义；不写死章节编号，也不强制增加不适用章节。
- 表后分支合入处理表，图旁步骤放入图中，风险归风险表；依赖图旁不重复汇总接口契约。图例及不能由图表达的必要说明按实际需要保留。
- 修改前后运行 [scripts/validate_detailed_design_content.py](scripts/validate_detailed_design_content.py)；与修改前副本比较时加 `--before`，输出报告可加 `--json`。除重复与归属候选外，`D005` 检查枚举表空泛措辞，`D006` 检查整列无实际约束的“取值限制”；两项不受长文字阈值影响。
- 脚本仅报告 `REVIEW` 候选；AI 对照对象、条件、动作、时机、结果和失败行为，判断重复、归属错误、必要补充或冲突，不凭相似度删除。
- 删除前必须指出必要信息的保留位置；存在独有条件时先合并。修改后核对差异，确保条件、时序、数值及失败行为没有丢失；核对记录不进入正式详设。
- 概览用途、图中必要动作、风险触发条件和不同接口各自的异常行为允许必要重复；相同标识符、不同条件下的相同动作不能单独作为删改依据。
- 完整流程、候选规则及误报边界见 [references/content-review.md](references/content-review.md)。分别报告脚本候选与 AI 语义结论，未命中不能表述为“全文无重复”。

### 2.3 全文格式校验

- 修改前后运行 [scripts/validate_detailed_design_format.py](scripts/validate_detailed_design_format.py)：`python <脚本路径> <详设路径> --template <当前模板路径>`；每次扫描全文，不只检查修改行。
- 脚本对照本次模板检查章节、逐项定义、说明块、表格、待确认项、围栏及图的基础格式，并复用文字长度与 Frontmatter 校验；支持 `--json` 和多个文件，允许的变体见 [references/format-validation.md](references/format-validation.md)。
- 全文审核自动执行 `F013` 图表意图标签校验：所有图中可见的代码名称须以“中文动作、职责或状态含义 + 换行 + 代码名称”展示。缺少意图、未换行或代码名称在前报错；中文是否准确对应源码仍须逐项复核。
- 单独审核架构图或非详设文档时，运行 [scripts/validate_diagram_labels.py](scripts/validate_diagram_labels.py)：`python <脚本路径> <文档路径> [其他文档路径] --json`，不套用详设章节模板。自动支持范围和人工复核边界见格式校验说明的“图表意图标签”。
- 架构图另行复核运行镜像、架构层与文件/模块归属，不能只区分 App/Boot。按源码路径、定义位置和回调注册核对分区及跨层箭头；概览用目录层级，调用细节标文件和符号。状态图用归属注释，不虚构层级状态。`F013` 只检查标签格式，不自动证明层级正确；逐图记录归属复核结果。
- 待确认事项按 §8 选择行为对比表或信息补充表；脚本检查条目归属、模板表头、固定行及顺序、必要场景内容和表后结论，不以格式通过代替语义判断。
- 退出码 0 仅表示机械格式检查通过，1 表示有 ERROR/REVIEW，2 表示输入或模板错误。修正 ERROR，逐项复核 REVIEW 后重跑；局部修改披露历史问题，不以部分检查通过宣称全文符合模板。
- 不为消除报错而放宽模板或删去必要内容；语义复核及 Mermaid 实际渲染仍按对应要求执行。

### 2.4 结构体注释校验

- 修改结构体前后运行 [scripts/validate_detailed_design_struct_comments.py](scripts/validate_detailed_design_struct_comments.py)：`python <技能目录>/scripts/validate_detailed_design_struct_comments.py <详设路径> [其他详设路径] --json`。
- `C001/C002` 检查结构体用途及逐字段注释缺失；`C003` 逐列核对字段表“含义”“具体内容”的文字覆盖，未匹配只报 `REVIEW`，人工区分遗漏与等义改写。
- 扫描全文 C/C++ 围栏，支持普通字段、数组、位域、函数指针及前置/行尾多行注释；合并代码块按类型小节匹配字段表。复杂嵌套、多成员声明、条件编译或无法映射的表格报 `C004 REVIEW`，不静默判通过。
- 脚本只读，输出文件、行号、规则及严重程度；退出码 0 为机械检查通过，1 为存在 ERROR/REVIEW，2 为输入错误。语义一致性、无表格时的内容完整性及未展开外部类型仍须人工核对；本脚本不替代全文格式校验。

### 3. 设计运行时序

- 先确定任务、中断、定时器、队列和回调之间的执行上下文及先后关系。
- 事件驱动或跨任务模块优先用 `sequenceDiagram` 表达跨上下文顺序；简单模块没有内部调用顺序时可以不绘图。只有多个执行上下文的整体关系无法由接口定义和时序图表达时，才补充精简执行上下文表。
- 每张 `sequenceDiagram` 必须在全部参与者声明之后、第一个调用箭头之前使用 `Note` 明确写出进入条件，包括触发来源、进入入口和必须满足的前置状态；没有额外前置状态时明确写“无额外前置状态”。不得只在图外正文说明进入条件；流程拆成多个子图时，每个子图分别说明自己的进入条件，以及承接上一子图的哪项结果或状态。
- 每张 `sequenceDiagram` 在本模块最后一个调用或返回箭头之后使用 `Note` 明确写出退出条件，包括本模块入口是否返回、最终状态或输出，以及异常分支在哪里结束。时序图在本模块稳定边界结束，不展开调用方返回后的任务循环、队列调度或下游内部处理。
- 时序图使用源码或已确认目标设计中的真实任务名和上下文。不得把推测的任务名、适配层或协调器写成既有组件；确需新增名称时先列为设计命名待确认项。
- 存在多个任务、ISR、定时器或回调上下文时，使用 Mermaid `box` 按真实执行上下文分组，并用 `activate`、`deactivate` 标出本模块函数或回调的实际执行区间。只有一个执行上下文时无需机械增加 `box`。
- 时序图中的本模块内部参与者必须能够回溯到模块文件组成中的运行时代码文件或已确认内部组件。仅提供声明、类型或宏定义的头文件不作为运行时参与者。
- 跨模块时序只画到对方模块的稳定边界。外部对象优先使用“模块调用方”“板级采样接口”“下游接收方”等通用职责名称；确需映射实现时，在中文职责之后换行标注实际模块或接口名，不展开对方内部解析、持久化、调度、通知分发或消费过程。
- 一条流程若完全由模块外部实现，不为补齐链路而画进本模块时序图；用边界文字说明外部逻辑如何决定是否或何时调用本模块，或链接到对应模块详设。
- 同步调用的下一条箭头从上一调用的接收方继续，接收方返回后再回到调用方，避免连续箭头无法对应实际执行点。异步消息使用虚线箭头，并在箭头或相邻 `Note` 中说明入队、唤醒和载荷语义；不得画成发布方直接调用接收任务，也不为补齐链路单独增加通用消息分发参与者。
- 一个 `sequenceDiagram` 只表达一条触发到输出的跨参与者主链。异常、校验失败、资源获取失败或消息投递失败在完成必要的清理、记录或返回后立即终止当前流程时，使用顺序 `break` 表达早退；成功路径直接写在 `break` 之后，不再用外层 `alt` 包裹后续全部步骤。
- 只有各分支仍会继续执行不同后续流程，或分支处理后需要汇合到共同动作时，才使用 `alt/else` 或 `opt`。完成早退简化后，`alt/opt` 有效嵌套不超过两层时保留为一张图；达到三层及以上时，再按独立触发阶段、跨执行上下文切换或稳定输入/输出边界拆成子图，不得按每个判断机械拆图。拆分后的每个子图必须独立标注进入条件和退出条件，并写清承接的结果或状态。
- 只发生在一个执行单元内部的算法、状态判定和结果映射放入对应函数说明，使用 `flowchart` 或决策表，不为规避时序图嵌套而机械拆成多个时序子图。
- 时序图文字按显示宽度换行：一个汉字按 2 列，英文字母、数字和符号按 1 列。参与者名称、箭头说明以及 `alt/else/opt/loop/break` 标题每行不超过 40 列；`Note` 每行上限为 40 列乘以实际跨越的生命线数量，跨越数量包含首尾及中间生命线。使用 `<br/>` 在语义边界换行，不拆分函数名、事件名或字段名；单个标识符超过上限时独占一行并保持完整。
- 运行时序只展示内部执行链和对外输出时机，不重复定义对外接口载荷。
- 时序图只高亮会影响后续判断或输出的关键数据读写：关键读取统一使用浅蓝背景 `rect rgb(235, 244, 255)`；清空、保存、替换、更新等关键写入统一使用浅橙背景 `rect rgb(255, 247, 230)`。普通调用、返回、校验、纯计算和事件发布不高亮；同一文档的颜色语义必须一致，并在第 4 章开头说明。
- 函数的调用时机、运行位置、阻塞性、可重入性、并发保护和副作用统一写在函数详细定义的“调用约束”中；事件和回调的触发及执行上下文写在事件详细定义中。第 4 章只保留时序图，不设置重复的“运行方式”、时序参数或并发汇总章节。
- “阻塞性”按整个调用链是否会等待外部条件或资源来判定。等待信号量、阻塞式互斥锁、队列、事件、延时或 I/O 完成属于阻塞；普通同步函数调用本身不等于阻塞。字段统一写“非阻塞”或“可能阻塞：等待对象，最长等待时间”；同步读写仅消耗执行时间且不等待时，将耗时约束写入时序参数或调用限制，不得在“阻塞性”中写“包含有界同步读取/保存”等执行内容。若下层同步接口内部存在等待，仍按阻塞处理。
- “并发保护”必须明确实际调用方或访问方、执行阶段或上下文、是否存在并发以及保护方式。确认无并发时统一写“仅由 `<调用方>` 在 `<阶段或上下文>` 调用，无并发调用，无需加锁”，不得只写“启动阶段单调用者”“单线程”等模糊结论；“仅调用一次”属于调用次数约束，应写入调用时机或异常处理，不能代替并发说明。存在并发时写明具体互斥锁、临界区、原子操作或队列、保护范围和必要的加锁顺序；使用阻塞式锁时与“阻塞性”列保持一致。
- 函数的“异常处理”统一使用“异常场景、判定条件、本模块处理、对外结果/后续状态”四列表格。每个独立异常或边界分支单独成行；无返回值接口在最后一列写状态变化、记录或后续调用限制。没有异常分支时仍保留一行并明确“无异常分支”，不得把多个条件、动作和后果压成一句话。
- 跨对象/跨上下文关系、锁顺序和临界区内禁止操作写入对应结构体的访问规则、函数调用约束或事件回调，不再次罗列相同读写和保护信息。资源范围限于本模块实际持有、读写或直接访问的对象，不展开外部模块内部队列、缓存和调度状态。
- ISR 只保留有界、不可阻塞的动作；任务切换、跨上下文数据语义、队列失败和配置切换屏障必须可解释。

### 4. 定义对外契约

- 接口概览只列其他模块稳定使用的函数、事件、回调和共享数据；内部辅助函数留在运行逻辑中。
- 接口概览分为 `2.1.1 函数` 和 `2.1.2 事件` 两个子章节，不使用“接口/事件”混合表。函数表使用“函数、调用方、接收方、用途”列；事件表使用“事件、方向、发布方、接收方、用途”列。回调按事件填写，并标明当前模块的输入或输出方向。
- 通知分发、队列发送、参数块读写等通用依赖接口不属于本模块的对外接口，应放入运行时序或第 1.2 依赖关系。
- 使用源码中真实的名称或已经确认的目标 C 函数名、类型名和通知类型，不使用“业务回调”“状态处理”等笼统中文占位，也不自行创造“协调器”“适配层”等项目角色。
- 函数标识符作为接口名称、小节标题、表格项或正文引用时统一写成 `function_name()`；函数原型保留真实参数列表，调用表达式保留实际实参。函数指针字段、回调类型、宏、事件、变量、文件名和类型名不追加括号。
- 结构体通过函数指针注入依赖时，字段定义表使用“字段、类型、是否必须、参数/返回值范围与定义、含义”。每个函数指针字段先说明函数指针自身是否必须、是否允许为 `NULL`；再逐一说明参数方向、参数指针空值约束和对象有效期、合法范围、单位、返回值范围、成功/失败语义以及失败时输出是否有效。函数指针自身的空值规则与参数指针的空值规则不得合并或省略；可选函数指针还必须说明其为 `NULL` 时的模块行为。
- 目标接口可以重构。新增名称在形成正文前标为设计建议并完成确认；确定后在目标详设中统一使用，不在每行重复附加“拟新增”“当前缺失”等实现进度。
- 按当前模板组织接口章节。关键类型应在函数和事件详细定义之前出现；不同模板有其他明确顺序时服从模板。
- “关键数据结构”只展开本模块定义的类型，以及由本模块负责维护的跨模块稳定契约；每个枚举和结构体各自使用一个小节，不得因为复用基础类型、定义相邻或共同出现在一个代码块中而合并说明。类型按依赖和职责排列：基础枚举与通用数据、输入契约、输出契约、运行配置、内部记录与模块总体。
- 枚举统一按“用途 → 类型定义 → 枚举值定义 → 枚举值规则”描述，每个值单独一行，写明数值和业务含义。“取值限制”只写具体使用条件；全表没有独立限制时省略该列，部分值没有额外限制时填“—”。删除“合法配置值”“合法检测方向”“合法未知态”等填充语，保留同格中的实际限制。
- 枚举值规则只补充表中未覆盖的输入、输出、状态保存或索引范围、哨兵/未知值处理及必要类型转换；没有独立内容时省略。初始化、通知时机和接口转换在对应章节定义，不在枚举小节重复解释或记录讨论过程。
- 结构体按当前模板的“用途 → 类型定义 → 字段定义 → 字段约束 → 实例与访问”组织；类型定义中的每个声明字段在字段表中单独一行。普通字段说明类型、范围/枚举、单位和含义；配置增加默认值和来源，函数指针使用专用字段表。只有没有独立信息时才省略后两个说明块，不保留空标题或无信息占位句。
- 结构体定义前增加用途注释，每个成员增加就近的 C 注释；将字段表“含义”和“具体内容”（存在时）完整补入对应注释，保留其中的单位、范围、特殊值、条件和限制。“同上”等依赖表格位置的表述须展开；表格保留，注释与表格同步维护，属于必要重复。
- 字段约束只定义初始值、字段关系、合法组合及状态变化后应保持或改变的成员值，不重复单字段说明。内存保存、复制、指针边界和并发保护归入实例与访问或具体接口契约；输入校验、处理流程和失败行为归入函数/事件。外部模块类型只在实际使用处链接定义方详设，不复制其定义、布局或所有权；本模块明确维护的跨模块稳定契约除外。
- 修订结构体前，按当前模板的“实例与访问填写细则”决定对象范围和适用标签。默认采用“保存方式、写入、读取、访问规则”的顺序，短句逐项分行，不使用六列横表，不给查询接口套用发送/接收角色；只有多个可能维护方之间确有责任歧义时，才在保存方式前增加“维护责任”，模块内部记录不得机械写“本模块”或模块名称；没有独立信息的标签可以省略，实际存在的共享访问或指针约束不能省略。
- 保存方式写具体的初始化、覆盖、可访问结束或释放条件；不将静态初始化误写成内存分配，不把“系统运行期”“单次发布”等泛称当作完整生命周期。存储是否存在与业务数值是否可用分开；消息/查询副本和原对象按具体函数或事件说明，不能继承模块内部记录的生命周期。
- 数据访问规则按 §2.2 的内容归属要求组织：单个结构体就近说明，纯组合成员引用承载类型；有独立访问规则的成员可就近定义，外层总体不重复内层规则。函数只补充调用契约及必要引用，事件补充传递和载荷可访问边界；时序保留关键动作，不额外设置并发章节。
- 枚举类型本身没有实例所有权，不设置“实例与访问”。
- 同一结构体在不同函数或事件中表示不同业务数据、且自身不携带区分字段时，禁止使用“由使用位置确定”等笼统描述。优先使用一条完整句子，按“结构体未保存的业务标识；各函数参数或事件对应的字段含义和单位”顺序说明。代码标识符使用反引号，不同使用场景使用分号分隔；只有单句过长或映射关系复杂时才拆成子列表，不机械增加无信息量的标签或层级。
- 模块存在配置功能时，在关键数据结构中定义实际消费的完整配置及必要嵌套稳定类型，说明字段、默认值、来源、保存方式和访问规则；配置读取、校验、采用和失败流程留在对应函数/事件。外部配置与运行配置不同时给出字段映射；配置参数表不能代替结构体定义。
- 同一文档的输入、输出事件及回调按模板组织用途、事件/回调原型、注册/传入方式、载荷定义、发布与接收约束；外部订阅可用“订阅示例”替代注册说明。同一事件族可合并，但不能省略各自契约。

- 示例使用已核对的接口参数和返回语义；订阅方回调及日志宏若为示意名称，须就地注明。不为示例新增包装接口、固定消费者或展开下游业务。
- 必要的注册时机用短注释说明；历史消息是否补发、注销和载荷有效期等示例不能表达的契约，按实际需要保留短句或引用，不重复已有定义。
- 补充内容统一按“载荷访问规则”“处理规则”的顺序组织：前者说明复制、访问期限和留存限制，零载荷时省略；后者使用“条件 / 处理结果”表，说明校验、状态变化、重复处理及控制使用条件，无额外规则时省略。发布次数与顺序放在“发布与接收约束”，不混入载荷定义；共用前提可用短句，已有规则以引用代替重复。
- 每个函数补全参数、返回值、调用上下文、阻塞性、可重入性、副作用和异常行为。
- 每个事件补全触发条件、发布方、接收方、传递方式、载荷可访问边界、失败和重复/顺序语义。载荷已有结构体定义时引用该类型，只补充事件专用限制；订阅的生效/注销条件与载荷可访问边界分别说明。
- 指针类型与指向数据的取值范围分开写；枚举的哨兵值、上限标记和无效值不得写成合法取值。
- 查询一致性快照的接口应在模块内部完成临界区保护，调用方不接触模块私有锁。模块内部所有相关写入使用同一保护，并一次提交完整快照；接口说明明确“内部已保护”。
- 协议命令、字节布局、查询回填和回复语义由独立协议文档定义，功能详设不设置“协议映射”章节。协议文档已存在时链接到实际文档；没有落点时只用普通文字说明外部配置边界，不创建空链接。
- 功能详设只定义本模块消费的配置、状态以及产生的输出，不展开协议解析、命令分发、参数事务或查询编码过程。

### 5. 选择事件交付语义

- 通知类型已经表达的业务状态不要在载荷中重复。
- 事件仅携带接收方完成本次处理所需的最小参数；不要默认附加 GPIO 电平、完整配置或诊断字段。
- 先根据需求确定交付语义，不把某一种方案写成通用答案：
  - **逐事件快照语义**：每一次转换或动作都必须被独立保留。事件携带发布时已经确定的最小值、动作或引用。接收方不得再读取当前配置重新解释旧事件。
  - **当前输出语义**：下游只关心处理时的最新状态。事件可以零载荷，仅用于唤醒；接收方通过查询接口获取当前输出的一致性快照。
- 采用逐事件快照语义时，说明值拷贝生命周期、顺序、重复处理。只有接收方确实需要完整配置时才携带完整快照。
- 采用当前输出语义时，发布方必须先原子更新输出，再发布通知；查询接口必须整体返回一致快照。明确延迟事件会读到最新值、中间值可能被覆盖或合并，以及该行为是否满足需求。
- 两种语义都要定义通知失败后的可观测性与恢复方式。不得用查询当前值补造一条已经丢失且要求逐次执行的动作事件。

### 6. 补齐实现约束

按实际适用范围覆盖：

- 不设置独立的“正常处理流程”章节。接口入口内部的算法和处理分支写入对应函数详细定义，复杂分支可在该接口说明中使用 `flowchart`；跨参与者调用顺序写入时序与并发章节。
- 状态迁移直接作为第 3 章。状态机只描述业务状态和业务转换；配置加载、缓存重建、重新计算等处理步骤放入对应函数说明或配置时序，不伪装成业务状态；
- 只有两个业务状态时直接使用迁移表，列出当前状态、事件/条件、下一状态、动作及异常路径；异常处理已在接口中定义时引用对应小节。多状态模块使用 `stateDiagram-v2`，表格仅补充图中难以清晰表达的规则，避免图、表与文字重复。设备复位、启动初始化等生命周期过程留在对应接口，不放入业务状态迁移图或表。
- 状态转换、初始化、去重、超时和恢复；
- 配置来源、唯一权威值、默认值、范围、事务提交和生效时机；
- 配置章节直接命名为“配置参数”。仅有一张配置表时不再增加同名子标题。参数列使用中文业务名称，实际字段统一放入独立的“变量名”列，不得在参数列中只写 C 变量名。
- 配置表每列只表达一个概念。仅当“写入生效”和“业务采用”确实存在时间差时才分列；全部参数采用相同规则时在表外统一说明，不逐行重复。
- 不为规避未分析的竞态自行增加“配置代次”或版本字段。确需版本标识时写明可观察问题、比较规则、溢出处理和存储代价；否则用明确的顺序、屏障和风险项表达；
- 任务/ISR/DMA 并发、单写者、临界区、消息顺序和队列满行为；
- 参数存储布局、主备份、完整性校验、升级迁移和写入寿命由参数管理或存储设计文档维护，功能详设不设置“持久化设计”章节；本模块只说明配置读取、运行时采用和失败返回契约；
- 引脚、电气参数、上下拉、板级转换关系和资源预算由独立硬件文档维护，功能详设不设置“硬件与资源约束”章节。软件必须依赖的输入量纲、回调前置条件或并发限制，分别写入接口、时序或并发定义；
- 调试接口、长期保留日志和可观测计数；过程日志覆盖关键状态变化和事件触发时刻，并明确在状态更新、事件入队前后的记录顺序；
- 功能详设不设置独立“异常处理与恢复”章节。函数失败写入返回值和异常行为，事件投递失败写入事件契约，配置失败写入配置采用规则；无法在本模块内闭合的跨模块问题进入风险清单；
- 测试步骤、验证矩阵和验收点由独立测试文档维护，功能详设不设置“验证要点”章节。

### 7. 在模块概述组织依赖关系

- 依赖关系在第 1.2 使用唯一的精简 `flowchart`，不另设依赖关系章节或重复关系图。
- 图固定分为“上游输入与请求” `subgraph`、居中的本模块和“下游使用方” `subgraph`；本模块可以是单一节点，也可以是仅包含本模块运行时组件的 `subgraph`。上游与下游区域不得混画为无方向的节点集合。
- 上游事件按“发布方 → 通知分发（实际存在时） → 本模块”绘制；同步服务请求从实际调用方指向本模块。查询依赖按“本模块 → 服务提供方”绘制，返回值只在理解边界确有必要时补画。
- 本模块的输出事件按“本模块 → 通知分发（实际存在时） → 下游使用方”结束。下游只写“下游订阅方”等稳定边界，不展开事件消费者后续的上报、组包、同步、重试或其他内部处理。
- 图中仅保留实际存在的角色。配置、定时器或通知分发若不直接调用本模块文件，必须增加“模块调用方”边界，不得把外部调度职责直接画到本模块。
- 外部节点使用已有模块名；无法稳定映射时使用“模块调用方”“板级接口”“下游接收方”等通用职责名称，不展开外部模块内部流程。
- 边标签先写“输入事件”“查询完整快照”“输出告警事件”等业务意图；需要对应代码时换行保留真实名称，如 `A -->|"查询完整快照<br/>snapshot_get()"| B`，使用引号保护括号。函数原型、参数和返回值仍放入接口定义。

### 8. 收敛风险与待确认

- 只保留会改变外部行为、接口、状态迁移、数据兼容或验收结果的未决项。
- 待确认项统一为“复选框问题标题 + 一张条目内表格 + 表后结论”，表格与结论缩进 2 个空格，表格前后留空行。未确认结论留空，不填“待确认”；已勾选项填写实际结论。按当前库的优先级规则分类，不自创级别。
- 参数背景列出场景的配置项、取值和单位，说明未参与本次判定的参数；配置变化写明前后值，不用默认值代替启用状态。无配置依赖时明确说明，不编造配置。用户要求完整配置时逐项对照配置参数表，不能只列争议参数。
- 有候选行为时使用“对比项、共同条件、场景 A、场景 B”表；场景列可追加冒号及具体行为。固定行依次为参数背景、决策差异、确认方，中间按需插入初始状态、具体场景或关键节点。至少一行并排写共同条件和 A/B 的具体结果；多个独立选择逐行标明分别选择，不暗示整列必须一起选。
- 没有候选行为、仅缺接口或证据时使用“项目、说明”表，固定行依次为参数背景、具体场景、已知情况、待确认内容、影响、确认方。直接列需补的接口、数值或约定，不强凑 A/B，也不将已确认规则重新列为选项。
- 场景写清初始状态、输入或操作及结果，假设示例注明“例如”；周期、通知延迟、故障窗口和处理耗时须明示为假设，不冒充实测故障或既定接口契约。时间问题只保留能体现差异的节点，不强制逐分钟展开；非时间问题按操作前后或分支结果比较。
- 共同条件只写一次，无场景差异的单元格可填“—”；参数背景、决策差异、确认方及信息补充表的固定行必须有实际说明。表外不重复参数背景、问题现象、影响和确认方式列表。计时计算、条件是否完整及选项能否决策仍须人工复核。
- 风险写明触发条件、影响、规避/恢复措施和状态。
- 风险入表前先核对触发条件在目标设计或锁定源码中是否真实存在。已经由设计消除的风险应删除；只有假设、缺少触发路径或无法说明影响的条目不保留。已确认接受的语义限制标为已确认，不继续伪装成开放问题。
- 来源冲突不得自行合并；说明各来源、可信度、影响面和需要谁确认。

## 溯源与知识库集成

- Frontmatter 字段、顺序和可选性完全服从当前知识库规范和目标详设模板。先以模板的字段及顺序建立白名单；规范允许的可选字段不等于当前详设需要的字段。不得凭历史文档、源码模块数量或“便于检索”等理由新增 `modules`、`version` 等模板外字段；只有目标详设模板明确包含，或用户明确授权时才可加入。模块文件及职责只在正文 §1.4 维护一份权威清单。
- 对源码支撑的详设，模板中的 `source`、`git_branch`、`git_commit` 必须同时存在并有实际值；非源码类详设仅在模板或用户明确允许时整体省略这三个字段，不得保留部分字段。
- 写入前和写入后均运行 [scripts/validate_detailed_design_frontmatter.py](scripts/validate_detailed_design_frontmatter.py)：传入目标详设和当前详设模板；非源码类详设追加 `--non-source`。校验器分别报告 YAML 语法、模板字段集合、字段顺序和字段值约束；任一项失败时停止交付并修正，不能仅凭 YAML 可解析宣称“Frontmatter 通过”。
- 需要记录源码参考基线时，`source` 优先使用锁定提交的仓库链接，并配合 `git_branch`、`git_commit`；这些字段只用于技术核对溯源，正文仍以目标设计为唯一叙述视角，不记录本机绝对路径或易失效的源码行号。
- 需求和关联模块使用可落地的双链；不要创建没有目标文档的空链接，也不要为本模块建立自链接。
- 新文档加入最近的 `_INDEX.md`；若当前库维护待审核清单，同步增加审核入口。
- 单文件体量、命名和图表规模遵循当前库规范；复杂主题拆分后只保留一份权威正文。
- 收到评审或外部答疑结论时，先读取最新完整版本和精确位置。只关闭已经回答的问题，未回答项继续保留。
- 已确认结论应改写为确定设计，并从开放问题中移除。同步更新库规范要求的需求、详设、索引、待审核入口和编译记录；Raw 原文保持不变，只在库允许时追加独立的评审证据记录。
- 可复用技能只沉淀处理方法，不写入某个项目的具体结论、路径、分支、提交或人员。

## 复核与交付

完整编写或正式复核时，读取 [references/review-checklist.md](references/review-checklist.md)。至少完成：

1. 逐节对照当前模板，删除不适用空章节，补齐缺失的接口字段和约束。
2. 按模板的内容放置规则收敛重复说明。检查字段约束与实例访问是否混写、标签是否有独立信息、保存或失效边界是否具体；删掉模板填充和重复流程，保留理解接口及关键时序所需的短说明。
3. 搜索模板占位符、笼统接口名、虚构项目术语、当前实现/改造叙述、未解释缩写和无依据的“必须”。
4. 交叉检查接口概览、详细定义、时序图、状态迁移、配置表、依赖图和风险清单是否一致。
5. 对全部图执行 `F013` 并逐项复核中文意图与源码名称、行为、顺序的对应关系；按文档及图序号记录标签格式、语义复核和渲染结果，未覆盖项不得记为通过。检查 Mermaid 块闭合并尽可能实际渲染；图中节点和参与者过多时拆图。
6. 按 §2.3 运行全文格式校验，再运行结构体注释、上下游边界和内容归属校验；区分机械检查、候选及 AI 语义结论。检查双链、正文体量和 `git diff --check`；分别报告 YAML 语法、Frontmatter 模板一致性、全文格式及实际渲染结果，不相互替代。
7. 最终报告修改文件、证据基线、仍开放的风险、校验结果和 Git 状态；没有授权时明确说明未提交。只有脚本的全部 Frontmatter 检查通过时，才可写“Frontmatter 通过”。
